# 性能检查与实现约束

性能检查使用当前提交的生产构建、独立浏览器和确定性的虚构账单。
不要向脚本传入真实账单，也不要将报告、截图或生成的工作簿提交到仓库。

## 运行

安装项目开发依赖，准备 Chrome 或 Chromium，然后在两个终端依次运行：

```sh
pnpm build
pnpm preview --host 127.0.0.1 --port 4173 --strictPort
```

```sh
pnpm performance --chrome /path/to/chrome --output artifacts/baseline.local
```

也可以通过 `CHROME_PATH` 指定浏览器。浏览器由使用者安装，脚本不自动下载。
固定同一浏览器版本与设备后再比较前后结果。

常用参数：

- `--mode navigation`：桌面与移动 Lighthouse 冷启动，默认各三次。
- `--reduced`：额外运行减少动态效果对照，不替代默认动效结果。
- `--mode workflow`：导入、搜索、重置、筛选、翻页，以及浏览全部图表后的搜索。
- `--counts 1000,10000,50000 --cpus 1,4`：默认数据规模；包含一万笔时，降速只测一万笔。
- `--mode snapshot`：一万笔看板的浅色、深色可访问性及截图。
- `--runs 1`：调试时缩短执行；正式比较至少三轮。

默认报告保存在 Git 忽略的 `artifacts/performance.local`。
报告包含版本、参数、原始 Lighthouse、工作流阶段指标与可访问性结果。
工作流的步骤总耗时包含输入与脚本等待，不能当作 INP；使用 Event Timing
与 web-vitals 的交互指标，上传耗时和主线程长任务单独比较。
业务流程只记录数字和资源路径，不记录交易内容、搜索词或分组名。

## 验收与解释

首页绘制错误不能计为零分，也不能删除后只保留成功结果。首页 Lighthouse
检查以各分类至少 95 分为门槛；看板另检查按钮名称、对比度、标题层级和
可见标签一致性。快照的审计集合不同，不直接与导航模式的 SEO 分比较。

性能比较记录中位数和范围，并核对数值对应的构建及参数。接近目标时增加
样本数，避免并行执行浏览器基准。交互先测初始状态，再测浏览全部图表后的
状态；懒挂载不能仅让首次测量好看。1 万笔和 5 万笔本机交互目标为 200 ms
以内，一万笔 CPU 4 倍降速先争取 300 ms，最终目标仍为 200 ms。
Worker 解析重点观察页面响应与最长任务，不能只比较总导入时间。

这些是实验室结果，不证明线上用户 Core Web Vitals 的 p75 达标。脚本不引入
线上遥测，也不测试 WebMCP 客户端兼容性。涉及 Agent 生命周期的变化还需要
在实际兼容浏览器中，按页面的手动授权流程验证工具发现、查询与撤权。

## 模块边界

- 性能脚本与生产代码分离；生成数据、浏览器采集、导航和工作流各自负责。
- 统计与过滤仍由纯模型提供，图表只接收汇总，不因滚动、分页或挂载而重建分析口径。
- 视口延迟加载保留布局空间；重新进入视口时必须使用最新数据、主题和尺寸。
- 热力图的全局色阶取自完整筛选结果，不能随可见年份变化。
- 后台解析复用同一解析器；上传协调负责任务生命周期和同步撤权，UI 只接收状态及动作。
- 账单、搜索索引和授权只在当前页面会话中存在；错误日志不得包含工作簿行内容。

每阶段修改通过 `pnpm lint`、`pnpm typecheck`、`pnpm test`、`pnpm build`
及相应浏览器检查后提交。计算或解析调整补充边界测试，用户可见流程变化同步 README。
